## Why the merge-base is stale (and why that matters)

The 2026-08-31 reconciliation was done as a **squash regraft**: `c5599c5af` "chore: reconcile fork with upstream through d1abff2" has a single parent (`59b1aa9fb`, fork-only) and carries the entire upstream tree state through `d1abff256` (2026-08-30) as one commit. It was then merged into master as `41b524f45`.

Consequence: upstream commits between July and Aug 30 are **in the fork's tree** but **not in the fork's ancestry**. Git's merge-base therefore stays at `8a058f9d7` (July 5), and the raw "1517 upstream-only" count is inflated — the real new upstream content is:

- `git rev-list --count d1abff2..upstream/master` → **422 commits** (Aug 30 → Sep 15).
- `git diff --stat d1abff2 origin/master` → 363 files — this is the *actual* fork-carried delta.

A naive `git merge upstream/master` would three-way against the July base and re-conflict on every July→Aug-30 upstream hunk that the fork already contains — thousands of spurious conflicts.

## Strategy: merge with a corrected merge-base (graft), not rebase, not regraft

Options considered:

1. **Rebase 156 fork commits onto upstream** — rejected. The 156 includes the 1M-line squash commit; replaying it is meaningless, and rebase rewrites the deployed history.
2. **Repeat the squash regraft** (checkout upstream tree, reapply fork delta as one commit) — works, matches precedent, but perpetuates the broken ancestry: next sync has the same problem, and `git log`/blame stay useless for upstream code.
3. **Merge with a local `git replace --graft`** — chosen. Locally graft `c5599c5af` so its parents are `59b1aa9fb` + `d1abff256`. This tells git the truth about what that commit contains. `git merge upstream/master` then computes merge-base `d1abff256` and only conflicts on real fork-vs-upstream overlap in the last 422 commits. The resulting merge commit has `ae0632997` as a real parent, so **future syncs get a correct merge-base natively** — the replace ref is a one-time local crutch and is not pushed.

Migration numbering: fork carries 7 fork-only migrations (0212–0218 in fork numbering), so every upstream migration ≥ 0212 is offset +7 in the fork (fork `0240_living_dreaming_celestial` = upstream `0233_…`). Upstream added 0234–0279 (46 migrations); they must land as **0241–0286** with `meta/_journal.json` idx/tag updated. `packages/db/src/check-migration-numbering.ts` enforces no dupes / strict order / journal match.

#### `heartbeat-comment-wake-batching` afterAll timeout (~90s → ~4s)

All 29 tests passed but the file took ~250s and its `afterAll` drain tripped the 30s hook timeout. Root cause was **not** a merge defect in the test or in `heartbeat.ts` (both are byte-identical to upstream), and not `reconcileStrandedAssignedIssues` (also identical; a clean upstream worktree requeues the same 2 continuations). It is an interaction between an upstream test fixture and a *deliberate* fork feature:

- Fork commit `53bcb2745` ("recover bridges across gateway restarts") raised `DEFAULT_CONNECT_MAX_ATTEMPTS` 3 → 7, giving a 2+4+8+16+30+30 ≈ 90s connect-retry budget so a run survives an OpenClaw gateway that takes 40–56s to start listening. Upstream has no retry ladder at all.
- The suite leaves stray `resumeQueued` runs pointed at fixture gateways that are already closed. Every attempt is `ECONNREFUSED`, which the fork correctly classifies as retryable, so each doomed run burned the full ~90s before failing with `openclaw_gateway_connect_timeout` — and `drainActiveRunExecutions` waits for it.

Weakening the default would undo the fork fix, and the upstream test file is unmodified by design, so the escape hatch is an env override consulted **after** explicit `adapterConfig.connectMaxAttempts` (so the adapter's own retry tests still exercise the real ladder) and **before** the default. `server/src/__tests__/setup-supertest.ts` sets it to `1` with `??=`, so any suite can still opt back in. Verified: file 90.5s → 3.7s on the two slow tests, 29/29 pass, no hook timeout; `openclaw-gateway-adapter.test.ts` 12/12; `packages/adapters/openclaw-gateway` 100/100.

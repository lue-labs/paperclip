## Why the merge-base is stale (and why that matters)

The 2026-08-31 reconciliation was done as a **squash regraft**: `c5599c5af` "chore: reconcile fork with upstream through d1abff2" has a single parent (`59b1aa9fb`, fork-only) and carries the entire upstream tree state through `d1abff256` (2026-08-30) as one commit. It was then merged into master as `41b524f45`.

Consequence: upstream commits between July and Aug 30 are **in the fork's tree** but **not in the fork's ancestry**. Git's merge-base therefore stays at `8a058f9d7` (July 5), and the raw "1517 upstream-only" count is inflated — the real new upstream content is:

- `git rev-list --count d1abff2..upstream/master` → **422 commits** (Aug 30 → Sep 15).
- `git diff --stat d1abff2 origin/master` → 363 files — this is the *actual* fork-carried delta.

A naive `git merge upstream/master` would three-way against the July base and re-conflict on every July→Aug-30 upstream hunk that the fork already contains — thousands of spurious conflicts.

## Strategy: merge with a corrected merge-base (graft), not rebase, not regraft

Options considered:

1. **Rebase 156 fork commits onto upstream** — rejected. The 156 includes the 1M-line squash commit; replaying it is meaningless, and rebase rewrites the deployed history.
2. **Repeat the squash regraft** (checkout upstream tree, reapply fork delta as one commit) — works, matches precedent, but perpetuates the broken ancestry: next sync has the same problem, and `git log`/blame stay useless for upstream code.
3. **Merge with a local `git replace --graft`** — chosen. Locally graft `c5599c5af` so its parents are `59b1aa9fb` + `d1abff256`. This tells git the truth about what that commit contains. `git merge upstream/master` then computes merge-base `d1abff256` and only conflicts on real fork-vs-upstream overlap in the last 422 commits. The resulting merge commit has `ae0632997` as a real parent, so **future syncs get a correct merge-base natively** — the replace ref is a one-time local crutch and is not pushed.
